## Prompt 管理平台（简历：2024.01—2025.08）

### 背景与职责

面向内部研发人员的 Prompt 管理与调试平台。从零建设；此前有需要的人各自写 Prompt，缺少标准化统一管理。提供资产管理、模板变量输入、模型参数配置、在线调试及历史查看。前期流程为会议确认需求细节、静态页面、对接后端、测试。

前端栈为 Vue 3、Vite、TypeScript、DevUI、Pinia、Vue Router、Axios、MateChat、@microsoft/fetch-event-source。对话界面后续使用 MateChat；先讲技术流程，组件选型可追问时补充。

### 用户确认的交互与实现

- POST SSE；接收新增文字，持续更新当前 AI 消息。
- 生成时限制再次发送；有停止操作，使用 AbortController；停止保留已输出部分，不继续生成；下方有重新生成入口。
- 重新生成时清空旧回答再生成；当前本地实现避免重复插入用户消息。历史中间轮次重生成的精确处理未确认，不照搬 ChatGPT 行为。
- 历史确实有状态机；等待、接收、完成、失败、停止等阶段统一管理，订阅同步页面。具体原始代码遗忘，用户担心被追问，需要补强。
- 前端适配不同模型的正文与思考内容；讨论过把 reasoningContent 包进 think 标记交给 Markdown 组件。具体模型字段及内部协议以实际实现核实。
- 身份、部门权限对接由其他人负责，不扩成个人亮点。

### 技术边界

原生 EventSource 以 GET 为主；项目使用 fetch-event-source 处理 POST。SSE 多轮通常每轮新请求，携带上下文，不需要因为多轮就换 WebSocket。主动 abort 仅确定前端取消，后端模型停止需要服务端传播取消。完成标志是业务协议约定，不能把 [DONE] 当成所有 SSE 的标准。

MateChat 提供展示及其内部动画；接口调用、协议适配、状态、消息列表归业务。tokens→AST→VNode 说明渲染流程，不自动代表增量解析或不重复解析旧文本。h 创建 VNode，Vue 更新真实 DOM。

改进设想：长回答的 Markdown 解析及渲染成本，考虑已完成内容与活动尾部的处理；先研究组件实际能力再设计。不是已实施成果，不声称 ChatGPT 使用哪个内部库。

### 性能：确认口径与限制

- 内部前端监控网站发现超过三秒的访问，排查资源加载与重复接口；重复接口可能是人员列表，名称不确定。
- 简历使用路由懒加载、公共请求复用、组件资源外置 CDN 等参与措施。
- 用户回忆常规优化效果有限，最终 DevUI 相关资源移出主包、CDN 单独引入后指标改善；具体改动的项目归属和配置需历史源码核实。
- 2024 年约 40.7 万次慢访问；团队按 2025 年前八个月测算全年约 31 万次，预计同比降约 24%。是慢访问次数的年度预估，不是实绩、个人独立贡献、单次耗时或不达标率下降 24%。
- 不能用访客量推测指标，不编优化前包体和提升比例。缺少对照时不因果归于某一改动。
- 监控提到 PerformanceNavigationTiming；明确是 onload，不是 unload。具体三秒指标公式和上报时机需核实，不能默认所有异步加载都算进 load 指标。
- CDN 外置不等于延迟／懒加载。普通 script 在启动脚本之前会阻塞解析，但缓存与资源路径可能改变整体效果；不得简单宣称一定更快。
- 当前观察过 main raw 6.06MB、估算传输约1.2MB、Network约1500KB；其他依赖尺寸单位和 Initial/Lazy 归属不全，不拼凑历史结果。
- 报表增多后按可视区域懒加载：IntersectionObserver、占位、防重复、筛选变化和失败处理，是后续改进设想，未确认为已上线。
- 公共数据用 RxJS 保存分发；回忆过 ReplaySubject(1)，最终准确类型仍待 import/new 位置确认。Subject 本身不会自动请求去重。
